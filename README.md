# The Crazy Game — AI Rules Assistant

A QR-accessed rules assistant for **The Crazy Game**. A player scans the code on
the box, lands on a mobile chat page, and asks a rules question. The answer comes
from Claude, working only from the two official reference documents in
[`/content`](content/). Every question and answer is logged anonymously so you can
see where playtesters get stuck.

```
Player's phone  →  Next.js chat UI  →  /api/chat  →  Claude (+ cached rules context)
                                                 ↘  MongoDB (anonymous Q&A log)
```

- **Public chat:** `/`
- **Admin log viewer:** `/admin` (one shared password)

## 1. Updating the rules content

**You never need to touch any code to update the rules.**

The two authoritative documents live here:

```
content/
  TCG_Master_Rules_Reference_v1-2.md      ← how the rules work
  TCG_Board_Layout_Reference_v1.md        ← where things are on the board
```

Both files are plain Markdown. The app reads them from disk at runtime and hands
their **complete contents** to Claude with every question — there is no separate
copy of the rules baked into the code, and no search index to rebuild.

### To update the rules

1. Edit the Markdown file (or replace it wholesale with a new version).
2. **Keep the filename exactly the same.** The two names above are what the app
   looks for.
3. Commit and push:
   ```bash
   git add content/
   git commit -m "Update rules to v1.3"
   git push
   ```
4. Vercel redeploys automatically. The new rules are live in a minute or two.

That's it. No code change, no rebuild step to run by hand.

### If you need to change a filename

Filenames are declared in one place — the `REFERENCE_FILES` list at the top of
[`lib/rules/index.ts`](lib/rules/index.ts). Edit the `filename` values there to
match your new files. This is the *only* reason to open a code file for a content
update, and the same list is where you'd add a third reference document.

> **Tip:** the more precise the documents are, the better the answers. Claude is
> instructed never to invent a rule — if something isn't covered, it says so. So
> if playtesters keep hitting "the references don't cover that", the fix is to add
> that ruling to the Master Rules document.

## 2. Environment variables

All six are required in production. Copy [`.env.example`](.env.example) to
`.env.local` for local work, and add the same values in Vercel under
**Settings → Environment Variables**.

| Variable | Required | What it is |
|---|---|---|
| `ANTHROPIC_API_KEY` | ✅ | Your Anthropic API key. Server-side only. |
| `ANTHROPIC_MODEL` | — | Defaults to `claude-sonnet-5`. Leave it alone unless you have a specific reason — see below. |
| `MONGODB_URI` | ✅ | MongoDB Atlas connection string. Server-side only. |
| `MONGODB_DB_NAME` | — | Defaults to `tcg_rules_assistant`. |
| `MONGODB_COLLECTION` | — | Defaults to `interactions`. |
| `ADMIN_PASSWORD_HASH` | ✅ | Hash of the admin password. Generated by a script — never the password itself. |
| `ADMIN_SESSION_SECRET` | ✅ | Random string used to sign the admin session cookie. |
| `RATE_LIMIT_PER_IP` | — | Requests per IP per window. Default `15`. |
| `RATE_LIMIT_PER_SESSION` | — | Requests per chat session per window. Default `10`. |
| `RATE_LIMIT_WINDOW_SECONDS` | — | Length of the window. Default `60`. |
| `NEXT_PUBLIC_APP_URL` | — | Only used as the default target for the QR-code script. |

> **About the model:** the project specification calls for **Claude Sonnet 5**
> because the rules contain multi-step conditional logic — bump sequencing,
> direction-dependent retreats, portal exceptions. `ANTHROPIC_MODEL` exists so you
> can pin a newer model later, not as a way to save money on a cheaper one.

**Never commit a filled-in `.env` file.** `.gitignore` already excludes them.

## 3. First-time setup

### 3a. Anthropic API key

1. Go to <https://console.anthropic.com> → **API Keys** → **Create Key**.
2. Copy the key (it starts with `sk-ant-`). You only see it once.
3. Add billing credit to the account under **Plans & Billing**.
4. Set it as `ANTHROPIC_API_KEY`.

### 3b. MongoDB Atlas

You own this account — the developer should not.

1. Sign up at <https://www.mongodb.com/cloud/atlas> and create a **free M0
   cluster**. Any region near your players is fine.
2. **Database Access** → **Add New Database User**. Pick a username and a
   generated password, and give it the **Read and write to any database** role.
   Save the password somewhere safe.
3. **Network Access** → **Add IP Address** → **Allow access from anywhere**
   (`0.0.0.0/0`). Vercel's serverless functions don't have fixed IPs, so this is
   required.
4. **Database** → **Connect** → **Drivers** → copy the connection string. It looks
   like:
   ```
   mongodb+srv://myuser:<db_password>@cluster0.abcde.mongodb.net/?retryWrites=true&w=majority
   ```
5. Replace `<db_password>` with the real password. If it contains any of
   `@ : / ? # [ ] %`, URL-encode them (e.g. `@` → `%40`).
6. Set the result as `MONGODB_URI`.

The database and the `interactions` collection are created automatically the
first time a question is logged — there is nothing to set up by hand.

### 3c. Admin password

The password is never stored anywhere, only a hash of it:

```bash
npm run hash-password -- "choose-a-strong-password"
```

That prints a line like:

```
ADMIN_PASSWORD_HASH=scrypt:16384:8:1:u77YyPKPjf...:UnmW-SxBWDl...
```

Copy the whole value into `ADMIN_PASSWORD_HASH`. Then generate the cookie signing
secret:

```bash
npm run generate-secret
```

Copy that value into `ADMIN_SESSION_SECRET`.

**To change the admin password later:** run `hash-password` again, update
`ADMIN_PASSWORD_HASH` in Vercel, and redeploy. Changing `ADMIN_SESSION_SECRET` at
the same time immediately signs out anyone already logged in.

## 4. Deploying to Vercel

### Initial deploy

1. Push this repository to GitHub.
2. At <https://vercel.com/new>, import the repository. Vercel detects Next.js —
   accept the defaults.
3. Before clicking **Deploy**, expand **Environment Variables** and add all six
   required values from [section 2](#2-environment-variables).
4. Click **Deploy**. You'll get a URL like
   `https://tcg-rules-assistant.vercel.app`.

### Redeploying

Any push to the default branch redeploys automatically. That is how rules updates
ship — see [section 1](#1-updating-the-rules-content).

To redeploy without a code change (for example after editing an environment
variable), open the Vercel dashboard → **Deployments** → **⋯** on the latest one →
**Redeploy**.

> Environment variable changes only take effect on the **next** deployment.
> Always redeploy after editing one.

## 5. The QR code

Generate the code that goes on the game box:

```bash
npm run generate-qr -- "https://your-app.vercel.app"
```

This writes two files to `public/qr/`:

| File | Use |
|---|---|
| `tcg-rules-assistant.svg` | **Give this to the printer.** Vector — scales to any size cleanly. |
| `tcg-rules-assistant.png` | 1024×1024 raster, for previews, slides and mock-ups. |

The code uses the highest error-correction level, so it still scans with a scuff
or a small sticker over one corner. Print it at least 2 cm × 2 cm, keep the light
margin around it, and test it with a phone before doing a print run.

If the deployment URL ever changes, re-run the command and reprint.

## 6. The admin page

Go to `/admin` on the deployed site and enter the admin password.

- **Log table** — every logged question and answer, newest first, 25 per page.
  Click any row to expand the full text.
- **Session column** — the first 8 characters of the anonymous session ID. Rows
  sharing that value came from the same visit, so you can read a conversation in
  order. Hover to see the full ID.
- **Download CSV** — exports every logged interaction, with
  `timestamp, sessionId, question, answer, model, latencyMs, turnIndex`. Values
  are properly quoted, so commas, quotes and line breaks inside an answer won't
  break the file. It opens cleanly in Excel, Numbers and Google Sheets.
- **Sign out** — clears the session. Sessions expire on their own after 12 hours.

### What is and isn't logged

Logged: the anonymous session ID, the question, the answer, a timestamp, and
technical metadata (model, response time, token counts).

**Not logged:** names, emails, accounts, IP addresses, or anything else that
identifies a player. There are no player accounts in the app at all. The session
ID is a random UUID generated fresh in the browser on each visit and thrown away
when the tab closes.

## 8. How it works

### Project structure

```
app/
  page.tsx                       Public chat page (Server Component)
  admin/page.tsx                 Admin page — checks the session server-side
  api/chat/route.ts              The one endpoint players hit
  api/admin/login|logout/        Admin session cookie
  api/admin/logs/                Log table data
  api/admin/logs/export/         CSV download

components/
  chat/                          Chat UI
  admin/                         Login form and log table
  ui/                            shadcn/ui primitives

lib/
  anthropic/                     Claude client, system prompt, prompt caching
  auth/                          Password hashing and session cookie signing
  csv/                           RFC 4180 CSV writer
  mongodb/                       Connection pooling and the log collection
  rate-limit/                    Per-IP and per-session limits
  rules/                         Loads the Markdown from /content
  validation.ts                  Request validation and size limits

content/                         ← the two reference documents
scripts/                         Password, secret and QR-code helpers
```

### The conversation

A visit generates a random session ID in the browser (`crypto.randomUUID()`). The
conversation lives only in React state: every request sends the full history back
to the server, and reloading the page starts a genuinely fresh chat. The database
is never used to rebuild a player's chat — it is purely an analytics log.

### Prompt caching

The reference documents are large and never change between questions, so they are
sent as a cached system prompt using Anthropic's `cache_control` mechanism with a
one-hour TTL. The first question of a session pays to write the cache; every
follow-up reads it at roughly a tenth of the input cost. The conversation history
and the new question stay outside the cached prefix.

This is why nothing request-specific — no timestamp, no session ID — may ever be
added to the system prompt: a single changed byte would invalidate the cache and
put the full cost back on every question. Token counts in the CSV export
(`cacheReadInputTokens`) let you confirm caching is working.

### Rate limiting

Each IP gets 15 questions per minute and each chat session 10, both configurable.
The limits are held in the server's memory rather than in Redis — with several
serverless instances the effective ceiling is a little higher than the configured
number, which is fine for its purpose: stopping a runaway loop or casual abuse of
a public URL, and capping the Anthropic bill.

### Error handling

A player always gets a friendly message, never a stack trace or an internal
detail. **A MongoDB failure never costs a player their answer** — the logging
error is recorded server-side and the answer is still returned. You'd notice it
as a gap in the admin table, not as a broken app.

## 9. Troubleshooting

**"I couldn't reach the rules assistant just then."**
Usually the Anthropic key or its billing. Check `ANTHROPIC_API_KEY` in Vercel,
confirm the account has credit, and look at the function logs in
**Vercel → Deployments → Logs** for the real error.

**Answers work, but the admin table stays empty.**
MongoDB isn't connecting. Check `MONGODB_URI`, confirm the password is
URL-encoded, and confirm **Network Access** in Atlas allows `0.0.0.0/0`. The
function logs will show `[chat] MongoDB logging failed`.

**"Incorrect password" on `/admin` even though it's right.**
`ADMIN_PASSWORD_HASH` was probably pasted incompletely, or edited by hand.
Regenerate it with `npm run hash-password` and paste the entire value. Also
confirm you redeployed after changing it.

**Claude says a rule isn't covered.**
That's the intended behaviour — it will never invent a ruling. Add the missing
ruling to `content/TCG_Master_Rules_Reference_v1-2.md` and push.

**"You're asking questions faster than I can answer."**
The rate limit. Raise `RATE_LIMIT_PER_SESSION` / `RATE_LIMIT_PER_IP` if
playtesters are hitting it legitimately — but check first that a page isn't stuck
in a retry loop.

**The build fails after a rules update.**
Content updates can't break the build. Confirm the filenames still match those in
[section 1](#1-updating-the-rules-content), and that the files aren't empty.
